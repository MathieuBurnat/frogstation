# ADR 0001 — Cloudflare Workers (assets statiques) plutôt que Cloudflare Pages

- **Statut** : accepté
- **Date** : 2026-09-26
- **Décideur** : Nino Croaks (DevOps)
- **Origine** : point R-01 du pré-audit sécurité (FRO-23), ouvert par Serious Robert
  (Cybersécurité). Le pré-audit demandait explicitement de trancher le mode de
  déploiement avant le premier déploiement, parce que le choix détermine si
  `public/_headers` est servi ou non.

## Contexte

Le site est 100 % statique : deux entrées HTML (`index.html`, `404.html`),
du CSS et du JS produits par Vite. Aucun rendu serveur, aucune API, aucun état.

Le pré-audit signalait un risque réel : un fichier `public/_headers` présent dans
le dépôt donne toutes les apparences de la conformité, mais ne protège personne
s'il n'est pas lu par la plateforme. Le pré-audit posait comme prémisse que
`_headers` est un mécanisme *Cloudflare Pages uniquement*, et qu'un déploiement
Worker se retrouverait donc avec zéro en-tête de sécurité.

## Vérification de cette prémisse

Elle n'est plus exacte. La documentation Cloudflare
(<https://developers.cloudflare.com/workers/static-assets/headers/>) indique pour
Workers Static Assets :

> The default response headers served on static asset responses can be
> overridden, removed, or added to, by creating a plain text file called
> `_headers`.

Avec une limite explicite, qui est le vrai point de vigilance :

> Custom headers defined in the `_headers` file are not applied to responses
> generated by your Worker code, even if the request URL matches a rule defined
> in `_headers`.

Autrement dit : `_headers` fonctionne sous Workers, mais seulement pour les
réponses d'assets statiques.

## Décision

**Workers avec assets statiques, et sans aucun code de Worker.**

`wrangler.toml` ne déclare volontairement **pas** de clé `main`. Le Worker est
un pur serveur d'assets. C'est ce qui rend la limite ci-dessus inoffensive : il
n'existe aucune réponse générée par du code, donc *toutes* les réponses sont des
réponses d'assets, donc toutes portent les en-têtes de `_headers`.

`not_found_handling: "404-page"` sert `dist/404.html` avec un vrai statut HTTP
404 sur les chemins inconnus — même comportement qu'attendait le README, sans
routeur côté client.

## Pourquoi pas Pages

- Pages n'est plus la cible recommandée par Cloudflare pour un nouveau projet ;
  `cloudflare/pages-action` est déprécé au profit de `wrangler`.
- Pages ne fait ici **rien de plus** que Workers : même lecture de `_headers`,
  même page 404, même build. Il n'y a donc aucun bénéfice à payer la dette d'une
  plateforme en fin de cycle.
- Un seul outil (`wrangler`) pour la production et les préversions simplifie le
  workflow de déploiement et réduit la surface d'actions tierces à épingler.

## Pourquoi pas un Worker avec code qui repose les en-têtes

C'était l'option de repli proposée par le pré-audit. Écartée :

- Elle ajoute du code exécuté sur chaque requête, donc une surface de bug et de
  revue, pour un résultat que la plateforme fournit déjà.
- Elle déplace la politique de sécurité dans du TypeScript compilé, moins
  auditable d'un coup d'œil qu'un fichier `_headers` en texte clair.
- Elle réintroduirait exactement la catégorie de réponses que `_headers`
  n'atteint pas.

## Conséquences

- `public/_headers` est le **seul** endroit où vivent les en-têtes de sécurité, et
  il est effectivement servi. Vite le recopie de `public/` vers `dist/`, qui est
  le répertoire d'assets déclaré ; vérifié sur un build local.
- **Règle de garde** : ajouter une clé `main` à `wrangler.toml` casserait cette
  propriété. Si un code de Worker devient nécessaire, les en-têtes devront être
  reposés dans ce code, et cet ADR devra être révisé.
- La vérification qui compte reste une **réponse HTTP réelle** sur la préversion,
  pas ce fichier ni `wrangler.toml`. Elle est à faire au premier déploiement,
  dans [FRO-19](/FRO/issues/FRO-19), et à présenter à la Cybersécurité.
- Secrets requis côté GitHub Secrets, jamais dans le dépôt :
  `CLOUDFLARE_API_TOKEN` (restreint au déploiement de ce seul projet, pas un
  token global de compte) et `CLOUDFLARE_ACCOUNT_ID`.
